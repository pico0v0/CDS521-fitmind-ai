推荐采用 Streamlit + Python + LLM API + 本地数据集 + 规则校验器。
Streamlit 前端

用户信息输入 / 一周计划展示 / 自然语言反馈

Python 业务处理层
用户画像解析

结构化需求


候选数据检索

动作、食材筛选




大语言模型规划器

生成训练和食谱方案、解释推荐、解析修改意图

规则校验 + 确定性营养计算

冲突检查 → 局部修复 → 再次校验

输出个性化计划

保留结构化记录，允许用户再次调整


为什么这样设计？
大模型负责理解语言、组织计划、给出解释，但不应独立决定所有事实和计算。

例如模型推荐了“杠铃深蹲”，系统必须检查用户是否有杠铃；用户对花生过敏时，系统必须检查配料是否包含花生及其衍生成分；营养数据则应由食材重量和数据库数值计算，而不是要求模型凭空估算。

技术上可以要求模型返回符合 JSON Schema 的结构化结果，降低数据格式不一致的问题，但仍要进行独立的业务规则验证。

3. 评价指标
指标	计算方式	研究目的
硬约束通过率	无违规计划数 ÷ 计划总数	衡量可靠性
编辑成功率	成功修改并通过校验次数 ÷ 修改次数	衡量调整能力
无关内容保留率	保持不变的无关元素 ÷ 应保留元素	衡量局部修改精度
营养计算误差	展示值与数据库复算值的差值	衡量计算一致性
人工可用性评分	2 位盲评者分别给出 1–5 分	衡量实际可用性
响应时间与成本	P50/P95 延迟、token 和费用	衡量工程开销

建议将硬约束通过率 95%、编辑成功率 85% 设置为初步项目验收目标，而不是预先假设能够取得的实验结果。

报告中最好同时加入失败案例分析。例如，当模型推荐了用户没有的器械，或者修改训练日导致时间冲突时，分别展示两种方法如何处理。

八、我建议你们从哪里开始
最先完成的不是漂亮的网页，而是 统一用户画像和周计划的数据格式，并确保计划能被校验器自动检测。

一旦这部分稳定，前端、AI、数据和实验四位同学就可以并行开发。之后只需要将大模型的结构化输出接入已经完成的校验流程，实验也能直接复用相同的数据结构。

最终答辩要让老师看到三件事：系统真的能使用、AI 确实承担了关键智能任务、实验能够客观说明方案的优势与局限。 这比单纯堆叠功能更能体现一门 AI 课程小组作业的完整性。
